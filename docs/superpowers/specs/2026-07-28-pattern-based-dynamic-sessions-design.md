# Pattern-Based Dynamic Sessions — Design

Date: 2026-07-28
Status: Approved (design), pending implementation plan

## Motivation

SlotFit's current model is a fixed, ordered list of muscle-group-scoped slots that
pre-fills from the last completed workout. Scott's actual training flow is the
opposite: walk in, assess what equipment is free, pick a warm-up (rower preferred),
then build supersets of complex exercises on the fly — anchor with whatever compound
station is available (cable row, pull-up, DB bench, leg press, hack squat), pair it
with an opposite body part for #2, sometimes add a #3. He wants the app to support
that dynamism while still keeping him on an overall strength-building path, on the
principle that repetition builds strength.

## Decisions Made During Brainstorming

1. **Progression is tracked per movement pattern**, not per exercise alone and not
   per muscle-group weekly volume.
2. **Gym interaction model: user picks the anchor, app suggests partners.**
   Availability drives exercise #1; the app handles antagonist pairing for #2/#3.
3. **A routine becomes a day plan**: warm-up slot + pattern-coverage goals + a
   superset-round count. No fixed exercise order; the session is built live.
4. **Variety dial: staple pool + rotation.** Each pattern has a small pool of proven
   staples; suggestions favor the least-recently-performed staple so each recurs
   often enough to progress. Occasional "try something new" candidates.
5. **This replaces the existing slot-based workout experience** (not a second mode).
6. **Implementation approach: clean-slate domain** (user-selected). New models;
   old tables retained read-only as history.

## Data Model

All new tables. Existing `routine_templates`, `routine_slots`, `workout_sessions`,
`workout_exercises`, `workout_sets` remain untouched as read-only history.

### movement_patterns (seeded, ~10 rows)

| Field | Notes |
| --- | --- |
| id | PK |
| slug | e.g. `horizontal_pull` |
| name | Display name |
| opposite_pattern_id | FK to self; drives antagonist pairing |
| is_neutral | True for Core, Isolation, Carry, Conditioning — valid as #3 with any pair |
| display_order | UI ordering |

Curated set: Horizontal Pull, Vertical Pull, Horizontal Push, Vertical Push,
Knee Dominant, Hip Hinge, Core, Carry/Locomotion, Isolation, Conditioning.
Opposites: horizontal pull ↔ horizontal push, vertical pull ↔ vertical push,
knee dominant ↔ hip hinge. Neutral patterns have no opposite.

### exercise_pattern_map

One row per exercise: `exercise_id` (unique), `pattern_id`, `is_override` (manual
correction flag). Generated by a seed script that rolls up the exercise database's
30 raw `movement_pattern_1` values plus `mechanics` and `body_region` into the
curated ten (e.g. raw `Knee Dominant` → Knee Dominant; `Elbow Flexion`/`Elbow
Extension` with Isolation mechanics → Isolation; `Locomotion`/cardio → Conditioning;
`Anti-Extension`/`Anti-Rotational`/`Spinal Flexion` → Core). Rows flagged
`is_override` are preserved on re-seed.

### day_plans (replaces routine_templates conceptually)

| Field | Notes |
| --- | --- |
| id, user_id, name, description | |
| warmup_preferences | JSONB ordered list of preferred warm-up exercise/equipment ids (rower first) |
| rounds_target | Target superset rounds for the day (e.g. 3) |

### pattern_goals (child of day_plans)

| Field | Notes |
| --- | --- |
| day_plan_id, pattern_id | |
| required | Required vs optional coverage |
| target_sets | Optional set target for the pattern |
| rep_range_min, rep_range_max | Rep range for double progression; defaults 8–12 when unset |

### training_sessions (replaces workout_sessions conceptually)

`id, user_id, day_plan_id, state (draft/active/completed/discarded),
started_at, completed_at, notes`. Warm-up is logged as a round whose single entry
maps to the Conditioning pattern.

### superset_rounds → round_entries → entry_sets

- `superset_rounds`: session FK, order. A round holds 1–3 entries; a one-entry
  round is a straight set. Supersets are structure, not a string tag.
- `round_entries`: round FK, position (1–3), exercise_id, pattern_id (denormalized
  at time of logging so later mapping edits don't rewrite history).
- `entry_sets`: entry FK, set number, weight, reps, time_seconds, completed.

### staple_exercises

`user_id, pattern_id, exercise_id, is_active, added_at`. Recency, load history,
and e1RM are always derived from session history, never stored here.

### exercise_preferences (blacklist)

`user_id, exercise_id, preference ('never')`. Hard-excluded from all suggestions
(e.g. barbell bench press).

## Suggestion Engine

### Anchor selection (round entry #1)

When a round starts, show staples grouped by uncovered pattern goals, most-needed
pattern first, each badged with its primary equipment. User taps what is free.
Full exercise search remains as fallback; selecting a non-staple queues an
"add to staples?" prompt for session end.

### Partner suggestion (entries #2 and #3)

- **#2**: candidates from the anchor pattern's `opposite_pattern_id` staple pool,
  ranked least-recently-performed first.
- **#3 (optional)**: candidates from neutral patterns or another uncovered goal,
  so a triple does not double-tax the antagonist pair.
- All suggestion lists apply, in order: exercise blacklist, injury restrictions,
  current equipment profile (bodyweight always available), weekly-volume guard
  (>20 sets/muscle group). The existing `not_recommended` "why not" payload carries
  over unchanged.
- One "try something new" candidate per list: a compound exercise from the broader
  database matching the required pattern and available equipment, visually
  distinct, never auto-selected.

### Existing rules carried forward

Bodyweight-always-available, injury-aware filtering (conservative, with
disclaimer), equipment profiles, and the "why not" feature all apply inside the
new engine exactly as documented in CLAUDE.md.

## Progression

Two layers:

1. **Per-exercise targets** (the in-session "what do I lift" answer): double
   progression from that exercise's own history — repeat last weight, add reps to
   the top of the rep range, then suggest a load increment. Displayed on the
   logging card: "Last: 3×10 @ 120 → Target: 3×11 @ 120".
2. **Pattern-level progress** (the "am I on the path" answer): estimated-1RM trend
   per pattern computed across all staples in the pattern, each exercise's e1RM
   normalized against its own baseline so swapping staples does not register as
   regression. Surfaced as per-pattern trend lines plus a weekly coverage view
   (patterns hit, sets per pattern).

Rotation-by-recency within the staple pool is the mechanism that reconciles
variety with "repetition builds strength": each staple recurs roughly every 1–2
weeks, keeping its double-progression chain intact.

## In-Gym Session Flow

1. Start a day plan → **warm-up card**: preference list in order (rower
   highlighted), tap what's available, log duration/intensity.
2. **Rounds loop**: anchor pick → partner suggestion(s) → alternate set logging
   across entries (A, B, [C], A, B, [C]…) with one shared rest timer per
   round-trip → close round → next round.
3. **Coverage tracker**: persistent pattern chips (covered / remaining / optional)
   showing what today still needs.
4. **Finish** → summary: pattern coverage, per-exercise PRs, pattern e1RM deltas,
   "add to staples?" prompts for new exercises.
5. Unfinished-workout **resume banner** on app load carries over as-is
   (localStorage check, banner not modal).

### Features that are retired

- Slot pre-population from last completed workout.
- "Save as New Routine?" divergence prompt (day plans hold goals, not exercises —
  there is no divergence to reconcile).
- Slot reordering and superset tags.

## Migration and API

- New namespace: `/api/v1/patterns`, `/api/v1/day-plans`, `/api/v1/staples`,
  `/api/v1/sessions` (with round/entry/set sub-resources), `/api/v1/suggestions`
  (anchor + partner endpoints).
- Old endpoints stay mounted read-only for history until the web app cuts over,
  then are removed.
- **Seed script**: builds `movement_patterns` and `exercise_pattern_map` from the
  exercise database.
- **Backfill script**: maps historical `workout_exercises` through the pattern map
  so recency and pattern progress work from day one, and derives initial staple
  pools (any exercise logged 3+ times becomes a staple in its pattern).

## Testing

- **Unit**: taxonomy rollup (every exercise maps to exactly one pattern;
  spot-check known exercises land correctly), suggestion ranking (opposite-pattern
  correctness, recency order, blacklist/injury/equipment exclusion, volume guard),
  progression math (double progression targets, e1RM normalization).
- **API**: CRUD for day plans/staples/preferences; session lifecycle including
  rounds with 1, 2, and 3 entries.
- **E2E (Playwright)**: one critical path — start day plan → warm-up → two rounds
  with partner suggestions → finish → coverage summary. Old slot-flow e2e tests
  retire with the flow.

## Out of Scope

- Real-time gym equipment availability detection (user's eyes are the sensor).
- Mesocycle/periodization planning beyond weekly pattern coverage.
- Android (web-first strategy unchanged).
- Auth (still localStorage-user MVP).
